## 首要修复项

1. `src/tudou_patrol2/src/tudou_vlm_agent2.py` 多处调用 `emergency_skip_next()`，类内没有实现。应先明确失败策略：记录失败目标、处理目标句柄、取消必要动作，再决定推进或终止，不能仅为了完成演示而将失败报告为成功。
2. 同文件两处 `get_gradient_logger()` 应改为 `get_logger()`。否则异常处理本身再次抛错，线程退出，后续任务索引无法推进。
3. 同文件 `process_vlm_and_report` 和 `upload_to_nurse_station` 重复定义。保留一份并检查调用行为。
4. `upload_to_nurse_station` 吞掉异常，未检查 HTTP 状态；外层仍上报“成果已上传”。应返回明确结果并决定重试、缓存或失败。
5. 图像等待缺少超时，`cv2.imwrite` 的布尔返回值未检查。没有图像时可能一直等待；保存失败时可能读取旧图像。
6. VLM `stderr=PIPE` 未消费，可能造成管道阻塞；`kill()` 后未 `wait()`；异常路径缺少统一清理。`select` 结合文本缓冲读取也需要仔细验证；采用字节流非阻塞读取与增量解码，或专用读线程会更清晰。
7. 25 秒/1.5 秒是等待可读的间隔，不是整个推理任务硬截止时间。需要单调时钟统计整轮耗时。
8. 未匹配紧急字符串就判为 NORMAL，可能把无效输出当正常。应加入 UNKNOWN/ERROR，并进行严格格式解析。
9. `is_patrolling` 是跨线程共享布尔标志，不是线程互斥锁；当前节点不是完整的线程安全状态机。建议由 ROS 执行器统一更新任务状态，耗时线程只回传结果。
10. 返回点失败后仍可能走到“就位初始点”的最终状态。任务完成、成功返航与任务终止需要区分。

## 丰富仓库的推荐顺序

### P0：让读者看懂、让正常和失败路径可信

- 根目录 README + 实物图 + 护士站截图（本次已提供）。
- 修复上述异常处理阻断项，至少覆盖导航拒绝、导航失败、无相机帧、推理超时、上报失败。
- 添加 60～90 秒完整任务视频：语音触发、导航、到点观察、护士站更新、返航。使用真实流程，避免只展示几个互不关联的片段。

### P1：让别人可以部署

- 提供护士站源码和运行入口；明确本地屏是否为浏览器展示或独立 GUI。
- 提供 `docs/deployment.md`：系统镜像、Python、ROS、NPU driver/runtime、RKNN/RKLLM 版本，以及模型来源、转换和单图验证命令。
- 提供 `docs/protocol.md`：11 字节下发 / 24 字节反馈逐字段定义、单位、大小端、校验算法与示例；确认下位机固件一致。
- 引入 `config/patrol.yaml`、`config/hardware.yaml`，通过 ROS 参数读取。只新增 YAML 文件不会自动消除源码硬编码。
- 完善 package.xml 描述、依赖、维护者信息。保留第三方许可和来源记录。

### P2：用测试证据展示工程优化

- 任务：请求数、完成数、失败原因、返航成功数与端到端耗时。
- 导航：测试路线、起终点实测误差、成功率及障碍条件。
- 模型：模型版本、量化方式、输入大小、冷/热启动、视觉编码耗时、TTFT 和解码吞吐分开统计。
- 网络：上报 RTT、失败率、超时次数和重试效果。
- 稳定性：持续时长、任务轮数、CPU/RAM/NPU/温度曲线与异常记录。
- 故障注入：相机断流、护士站离线、模型子进程退出、目标不可达；验证任务状态不会误报成功。

建议新增结构为 `docs/deployment.md`、`docs/protocol.md`、`docs/benchmarks.md`、`config/`、`scripts/`、`tests/`；这些是后续计划，本次没有创建虚假的实现或测试结果。
